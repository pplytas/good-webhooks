# What "1.0" should mean for good-webhooks (research, 2026-10-25)

Labels: **[F]** = verified from a primary source or the npm registry / GitHub API on 2026-10-25. **[S]** = secondary source (news, search summary), treat with care. **[I]** = my inference, not a fact.

Registry dates are `time` entries from `https://registry.npmjs.org/<pkg>`. "0.x length" = first npm publish to first stable 1.0.0 (or to today).

---

## 0. Headline findings

1. **[F] "1.0" is rarely defined by a checklist.** Hono's v1.0.0 release notes list 11 PRs and no criteria; Drizzle's release page states none; Kysely and graphile-worker publish no 1.0 plan. Better Auth is the only one with a stated meaning ("production use, APIs stable until next major", via a secondary summary, [S]).
2. **[F] Infra libraries with a database schema stay 0.x for years**: graphile-worker (0.x since Mar 2019, now 0.18.0), Kysely (0.x since Feb 2021, now 0.29.7), Drizzle (0.x since Sep 2021, 1.0.0-rc.5 on 21 Oct 2026, 0.45.4 still `latest`). Their release notes list breaking changes in minors.
3. **[F] A 1.0 is not a freeze in practice.** pg-boss shipped 12 majors in 9 years (v12.0.0 on 2025-11-09; a `maint-v10` dist-tag exists). Vitest went 1.0 (Dec 2023) to 5.0 (Sep 2026). Better Auth's 1.7 RC lists many breaking changes inside a 1.x minor. What 1.0 buys is a promise about notice and migration, not "never change".
4. **[F] good-webhooks already has much of what comparable projects lack**: OIDC trusted publishing with provenance, private vulnerability reporting enabled, SECURITY.md, branch protection with required checks, upgrade rehearsal against the previous published package, chaos tests, a published benchmark, an Agent Skill, llms.txt, a written stability policy, ADRs.
5. **[F] Verified gaps in the repo today**: no Dependabot/Renovate config, no CodeQL, no OpenSSF Scorecard workflow, no `attw`/`publint` run in CI, no CODEOWNERS, `.github/` holds only `workflows/` (ci.yml, release.yml); the performance doc itself says large history is "not proven"; Dependabot alerts endpoint returns 404 (likely disabled, [I] confirm in repo settings).
6. **[I] The biggest 1.0 risks are not features.** They are (a) the host-implemented interfaces (`ManagementRepository`, `EndpointSource`, `EndpointManagement`), which broke in 0.3.0 when a method and a parameter were added, so any future addition is breaking for custom implementers; (b) unproven behaviour at large history size and over long soak; (c) no second person who can publish or triage.

**[I] Reading the table.** Products where the author wanted trust fast went 1.0 in 4 to 17 months (Hono, Better Auth, Inngest, pg-boss, Fastify). Libraries that own a schema and migrate user data (graphile-worker, Kysely, Drizzle) delayed for years because they kept needing breaking changes. good-webhooks owns a schema and has the 0.x discipline of the second group, but the calendar of the first (17 days since the first release on 2026-10-08). The honest differentiator is the upgrade path, which is already rehearsed in CI.

## 4. Supporting notes by research question

### Semver, deprecation and support norms

- [F] Fastify: >= 6 months LTS per major, security 6 months after the next major, breaking changes in minors allowed if documented. Svix v2: v1 gets security fixes "for a while". AWS Lambda: 180 days notice before runtime deprecation. Repo policy: previous minor gets security fixes for 3 months after next minor. [I] For 1.x, "previous major gets security fixes for 6 months after the next major" fits the norm and is easy for one maintainer to honour.
- [F] Repo policy treats dropping a Node/PG version as breaking, which is the strict reading. Keep it.

### Types, packaging and supply chain

- [F] Run `attw` and `publint` on the tarball (M3). Repo already rehearses the exact archive with fresh consumers (`pnpm test:package`) and runs `pnpm audit --prod` before publishing.
- [F] Provenance: automatic with trusted publishing on GitHub Actions for public repos. SLSA build levels: L1 provenance exists, L2 hosted build with signed provenance, L3 hardened builds (the page I fetched is the retired v1.1 text; [I] the current spec revision may differ, and mapping npm provenance to a level is not stated there).
- [F] OpenSSF Scorecard checks relevant here: Dependency-Update-Tool, SAST, Security-Policy, Signed-Releases, Token-Permissions, Pinned-Dependencies, Fuzzing, CII-Best-Practices, SBOM. One-person blockers: Code-Review, Contributors.

### Verification bar (what others publish)

- [F] graphile-worker: a documented perf harness and throughput numbers; warns performance depends on keeping the jobs table small.
- [F] pg-boss: CI, coverage, Compose files for Citus, CockroachDB and YugabyteDB; no soak or fault-injection report.
- [F] Search found no Jepsen-style analysis of any Postgres-backed queue library. Blog posts only discuss duplicates, lost jobs and non-FIFO behaviour of `SKIP LOCKED` [S].
- [I] good-webhooks is already ahead on upgrade rehearsal and chaos. The missing pieces are history-size load, long soak, contention at higher worker counts, and property/fuzz tests (M7, S3).

### Governance and single-maintainer signals

- [F] pg-boss: one maintainer, funded through GitHub Sponsors with named sponsors; MIT "always will be". Kysely: one publisher, backport branch. graphile-worker: paid Worker Pro funds the project. Fastify: organisation plus commercial EOL support. Scorecard docs: one-person projects cannot pass Code-Review or Contributors.
- [I] Signals adopters look for: a security contact and response times, a stated support window, more than one person with publish rights, a funding or sustainability line, release cadence evidence, and a changelog that names breaking changes. Cheap mitigations: SECURITY.md with SLAs (M9), SUPPORT section with maintenance windows (M11), second npm owner and GitHub admin (S8), keeping releases fully automated via OIDC (done) so a backup can ship, a "what happens if the maintainer stops" paragraph, GitHub Sponsors.

### Documentation and DX

- [F] llms.txt (proposed 2024-09-03, updated 2026-08-10) and Agent Skills spec are stable enough that the repo's existing assets satisfy them; keep them current per release.
- [F] TypeDoc 0.28.20, Changesets 3.0.3 are current; neither is required for credibility (N1, N2).
