# good-webhooks competitive feature-gap analysis

Checked: 2026-10-25 (all prices, stars and release dates are as of that day, Europe/Athens).
Method: official docs and pricing pages (WebFetch), GitHub API for stars, license and latest release, npm registry for versions, plus the good-webhooks repo itself for its own row.
Legend: "n/v" = not verified (the page I could read did not say; do not read it as "no"). "no" = documented absent, or the vendor lists it as unsupported. "(V)" = vendor-authored comparison page, treat as a claim. "Ent" = Enterprise tier only.

Reference row, good-webhooks 0.4.0: embedded library, your PostgreSQL 16-18, MIT, Standard Webhooks signing, 7 attempts (5s/5m/30m/2h/5h/10h/10h, ~28h), retries all non-2xx except 410, Retry-After on 429/503, endpoint auto-pause (5 days failing or 410), replay, attempt log, URL policy with DNS-pinned connect (blocks private ranges), secret rotation with grace, scopes, maxEndpoints, `runOnce()` and `prune()` (found in repo docs, not in the brief), Better Auth plugin, `good-webhooks/verify`.

## 2. Facts versus inference

Verified facts worth keeping in mind (primary sources in section 6):

- Four embedded TypeScript libraries now compete directly: CommitCourier, Postel, @xtandard/webhooks and good-webhooks. All four are tiny (0 to 4 stars). CommitCourier (Postgres, MIT, Standard Webhooks, DLQ, circuit breaker, OTel, LISTEN/NOTIFY, `doctor` CLI, pg/Knex/Drizzle/Prisma adapters) is the closest rival; its README names Postel but not good-webhooks.
- xtandard uses Svix's retry schedule minus its final 10h step and the same 5-day auto-disable rule, and ships a Svix-style React portal. Svix, xtandard and good-webhooks therefore share one de facto policy.
- Standard Webhooks spec says to use Retry-After and treat 410 as "disable now". The spec example schedule runs longer than ours (adds 14h, 20h, 24h).
- Svix gates mTLS/OAuth, FIFO, custom retry schedule, OTel log streaming and custom signature scheme at Enterprise. Convoy gates OAuth at Premium and mTLS at Enterprise. Outpost has no mTLS. EventBridge API destinations do not support mTLS. So receiver mTLS/OAuth is a premium/enterprise feature everywhere, not table stakes.
- Outpost explicitly leaves per-tenant rate limiting and transformations out of scope.
- Hook0 is not Standard Webhooks compatible (per Svix's page, vendor claim). Hook0 and Convoy are source-available (SSPL, ELv2), not OSI open source. Svix server and Outpost are MIT / Apache-2.0.
- No Better Auth community plugin delivers outbound webhooks except good-webhooks (community-plugins-data.ts lists good-webhooks; all other webhook mentions there are payment-provider inbound handlers). The TurboStarter guide shows people hand-rolling this on top of Better Auth API keys.
- Supabase pg_net has no retries, 6h response retention, ~200 req/s ceiling, but does queue the request only on transaction commit (a transactional-enqueue pattern for plain HTTP).

Inference (my judgment, not sourced):

- Most TS developers choosing today will compare Svix hosted first, then a hand-rolled queue (BullMQ, pg-boss, Inngest, QStash), then a library. The library niche is real but empty of a clear winner; maturity and trust, not features, is the gap.
- The brief's claim that nothing else ties publish to the app's transaction is no longer fully true: CommitCourier, Postel, outboxer and Dloizides.Webhooks.AspNetCore (.NET) do. The defensible differentiators are Better Auth, endpoint management with scopes/encrypted secrets/rotation, the upgrade-path rigor, and receiver `parseWebhook` typing.

## 3. Table stakes good-webhooks lacks

Ranked by how many serious alternatives have the feature and how cheap it is for a library.

1. Delivery history and resend for the endpoint owner. Svix, Outpost, Convoy, Hook0, Hookdeck, Knock, xtandard, Stripe all give it (portal or dashboard). good-webhooks records attempts but exposes no history/replay routes in the Better Auth plugin and no aggregate stats. This is the one gap every dogfood finding points at. Cheapest fit: JSON routes plus client methods (list deliveries, list attempts, replay, stats). No UI.
2. Dead-letter inspection and redrive API. CommitCourier, xtandard, Svix (Redis), QStash, pg-boss, Cloudflare Queues, EventBridge, BullMQ all have an explicit "failed/dead" list with redrive. good-webhooks has abandoned deliveries with no named API. Cheap: a documented list and bulk replay with a cap (CommitCourier caps mass replay for safety).
3. Per-endpoint custom headers. CommitCourier (encrypted at rest), Hook0, Svix, Hookdeck, Spatie. Needed by receivers that sit behind an API gateway. Cheap if stored with the existing secret encryption. mTLS and OAuth are not table stakes (see section 2).
4. OpenTelemetry/metrics. Outpost (all tiers), CommitCourier, Convoy Premium, Svix Ent, QStash Prod Pack. good-webhooks has `onAttempt` hooks, so an optional OTel adapter or documented recipe closes most of it.
5. Per-endpoint concurrency or rate cap. Svix, Convoy, Hookdeck, QStash, EventBridge, Inngest all have it; Outpost and Hook0 do not, and no embedded TS library found has it. A single `maxConcurrentPerEndpoint` is the minimal form. Medium priority.
6. Event schema export. Svix event types with JSON Schema drive its portal catalog and "send example" feature. good-webhooks already holds Standard Schema validators, so JSON Schema export or an event-type list endpoint is nearly free.
7. Local dev loop. Stripe CLI, Svix listen/Play and Hookdeck CLI set the expectation. A library does not need a tunnel, but a "send test event to this URL" command or a documented receiver recipe covers the same need (test events already exist).
8. Lower-latency wake-up (LISTEN/NOTIFY). CommitCourier and txob have wake-up signals; polling-only costs up to one poll interval per delivery. Medium-low.
9. Receiver-controlled delivery. Svix honors `webhook-delivery: abort-message` and `disable` response headers. We already honor 410. Optional, cheap.

Already at parity or ahead (per the matrix): Standard Webhooks signing, Retry-After, 410 handling, replay, auto-pause, secret rotation with grace, SSRF/DNS pinning, retention (`prune`), serverless-friendly `runOnce`, endpoint caps.

## 4. Differentiators (what most alternatives lack)

- Publish rides the app's own pg client/transaction: among TypeScript products only CommitCourier, Postel and the generic outbox libs share this (outside TypeScript, Dloizides.Webhooks.AspNetCore does too). Svix, Hookdeck, Convoy, Outpost, QStash, Inngest, BullMQ cannot join a local transaction (CommitCourier's README makes the same point).
- Better Auth plugin for user-managed endpoints with authenticated routes, a typed client, and the full adapter matrix (pg, mysql, sqlite/libsql, mongodb, mssql). No other product found does this; it is already listed in the Better Auth community plugins.
- Standard Webhooks both ways (signing and `parseWebhook` typed receiver). Svix, Outpost, Webhook Relay, CommitCourier, xtandard do signing; typed event parsing on the receiver via the same schemas is rarer.
- No infrastructure beyond the Postgres you have: Svix needs a server plus Postgres (Redis optional), Outpost needs Redis + Postgres + a queue, Convoy needs Postgres + Redis, BullMQ needs Redis.
- Endpoint management as a first-class part of the library (scopes, caps, URL policy, encrypted secrets with key rotation). CommitCourier has inline or registered endpoints but no scoped, user-facing management; Postel has admin handlers but no auth-framework integration.
- Rigor signals the small competitors lack: versioned schema migrations with upgrade rehearsals in CI, chaos tests and a published benchmark.
- Price: free and MIT, against Svix $490/mo Pro for static IPs, white-label portal and 99.99% SLA, and Hookdeck $499/mo Growth.

## 5. Scope creep for a library, and why

- Hosted service, multi-region delivery, SLAs, SOC 2/HIPAA, SSO/SAML: product and company features, not library features. Postel's positioning says the same ("never a hosted offering").
- Static egress IPs: a property of where the worker runs, so it does not apply. Document "run the worker behind your NAT/egress proxy" instead.
- Full dashboard and white-label receiver portal as a packaged product: Svix, Outpost and xtandard ship one, but it ties the library to a UI stack, a theming surface and a security surface. Provide the JSON API and let the host build UI. (xtandard shows the cost: its own React package, token minting and CSS.)
- JavaScript payload transformations: Svix and Convoy run user JS in a sandbox (Convoy gates it at Premium); Outpost leaves it out of scope. Sandboxing user code is a large security burden, and a library caller can transform in their own code.
- Non-HTTP destinations (SQS, Kafka, EventBridge, S3, RabbitMQ): Outpost's differentiator, wrong direction for this library.
- mTLS and OAuth client-credentials to receivers: Enterprise-gated at Svix and Convoy; heavy secret and token-cache handling. Custom headers cover most real cases.
- Strict FIFO per endpoint: Svix limits it to about 20 msg/s per FIFO endpoint and gates it at Enterprise, and it blocks the queue behind a failing message. Stripe does not guarantee ordering either. A sequence number in the payload plus receiver-side guidance is cheaper. If ever built, make it opt-in per endpoint.
- Multi-database and multi-language ports (Postel's roadmap, xtandard's ten backends): spreading thin is the exact failure mode a single maintainer should avoid. PostgreSQL-only is a strength.
- Workflow engine features (debounce, batching, singletons, durable steps): that is Inngest/Temporal territory.
- Inbound webhook receiving/relay (Hookdeck gateway, Webhook Relay, Postel): different product. `parseWebhook` verification is enough.
