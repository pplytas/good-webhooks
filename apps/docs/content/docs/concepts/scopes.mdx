---
title: Scopes
description: A scope is a namespace that isolates endpoints and events. It never grants access by itself.
---

Every endpoint and every published event belongs to a scope. Publishing in a scope reaches only endpoints registered in that same scope. That is how one installation serves many customers without cross-talk.

| Scope             | Value                          | Typical owner              |
| ----------------- | ------------------------------ | -------------------------- |
| Application scope | `null`                         | Your platform itself       |
| Named scope       | `{ type: 'user', id }`         | One signed-in user         |
| Named scope       | `{ type: 'organization', id }` | One tenant or team         |
| Named scope       | `{ type: 'anything', id }`     | Whatever your domain needs |

Application scope is its own namespace, not a parent of the named scopes. Publishing in application scope never reaches a user's endpoints, and a named publication never falls back to application endpoints. Use the endpoint owner's exact scope.

## Selecting a scope

Each API selects scope differently:

<Tabs items={['createWebhooks / createDelivery', 'Management provider', 'Better Auth routes']}>
<Tab>

The root instance uses application scope. `forScope()` returns the same methods bound to a named scope.

```ts
await webhooks.publish({ type: 'invoice.paid', data }) // application scope

const tenant = webhooks.forScope({ type: 'organization', id: orgId })
await tenant.endpoints.create({ url, eventTypes: ['invoice.paid'] })
await tenant.publish({ type: 'invoice.paid', data }) // reaches that org's endpoints
```

</Tab>
<Tab>

Direct provider methods take the scope as their first argument. Pass `null` for application scope.

```ts
await management.create(null, input)
await management.create({ type: 'organization', id: orgId }, input)
```

</Tab>
<Tab>

An omitted `scope` means the signed-in user's personal scope. Other scopes are checked against the session. See [permissions](/docs/better-auth/permissions).

```ts
await authClient.goodWebhooks.create({ url, eventTypes }) // current user
await authClient.goodWebhooks.create({ scope: { type: 'organization', id }, url, eventTypes })
```

</Tab>
</Tabs>

## Scopes do not authorize

<Callout type="warn">
  `forScope()` and the direct provider methods trust their arguments. Authorize the caller in your
  application **before** choosing a scope, and never pass an unchecked ID from a request body.
</Callout>

The Better Auth routes are the exception: they check the session, organization membership, and permissions on every request. Its trusted provider returned by `createBetterAuthManagement()` bypasses those checks, which is what a worker needs.

## Scope limits and identity

- `type` is 1 to 64 characters, `id` is 1 to 200 characters. Both are nonblank with no null bytes.
- The same `id` under two different `type` values is two different scopes.
- Each scope holds at most 1,000 live endpoints.
- Idempotency keys are unique per scope, not globally.

## When an owner goes away

The Better Auth plugin retires a user's endpoints when the user is deleted, and an organization's endpoints when the organization is deleted. For standalone management, call `removeScope(scope)` on a `createPostgresManagement()` provider from your own owner-deletion workflow. See [manage endpoints](/docs/guides/endpoints#when-a-tenant-leaves).
