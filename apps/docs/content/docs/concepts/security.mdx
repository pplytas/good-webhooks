## Two kinds of secrets

| Secret                         | Held by                                           | Used for                                            |
| ------------------------------ | ------------------------------------------------- | --------------------------------------------------- |
| **Signing secret** (`whsec_…`) | The receiver, and endpoint management (encrypted) | Signing each request. The receiver verifies with it |
| **Storage encryption key**     | Your app and worker processes                     | Encrypting signing secrets in management storage    |

Standalone PostgreSQL management takes a 32-byte key from `generateEncryptionKey()`. Better Auth management uses the auth instance's `secret` or versioned `secrets` instead.

`create()` and `rotateSecret()` return the plaintext signing secret once, and reads never include it. Give it to the receiver over a secure channel and never log it. Rotating a signing secret changes what the receiver verifies; rotating the storage key does not. See [key rotation](/docs/operations/key-rotation).

## Signing

Requests follow the [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md) specification:

```http
webhook-id: 7a0c3f3e-5b2c-4f8e-9d1a-2e6b8c4d9f10
webhook-timestamp: 1760000000
webhook-signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj6D2hFcTjqRVo=
```

The signature is HMAC-SHA256 over `{id}.{timestamp}.{body}`. During a secret rotation the header carries one signature per usable secret, and `parseWebhook()` accepts the request if any matches and the timestamp is within five minutes.

## Destination checks

Registration requires HTTPS and rejects credentials in the URL and unsafe IP literals. Standalone PostgreSQL management also resolves DNS at registration. Because DNS can change later, the worker resolves the hostname again before every connection, rejects private and otherwise unsafe addresses, connects to the address it checked, and never follows redirects.

`allowLocalhost: true` permits plain-HTTP loopback destinations for local development and opens no other private ranges. [Custom senders](/docs/guides/custom-senders) must implement the same protection themselves.

## What you must enforce

- **Authorization.** Scopes keep endpoints and events apart; they don't check permissions. Check the caller before `forScope()` or any provider method. See [scopes](/docs/concepts/scopes).
- **Trusted sources.** `management.source` returns plaintext signing secrets. Keep it in server code.
- **Receiver body limits.** Bound the request body before buffering it. `parseWebhook()` rejects bodies over 512 KiB, but only after your server has read them.
- **Receiver deduplication.** Verification proves who sent the bytes, not whether you already processed them.
- **Delivery history.** Stored payloads and response bodies may contain user data. Treat them like any other application data.
