description: At least once, no ordering. What a successful publish promises, how retries work, and how endpoint changes affect queued work.

## The rules

1. **Accepted means stored.** When `publish()` returns, the event and its recipients are committed, or written in your transaction and committed when you commit.
2. **At least once.** A receiver may get the same event more than once.
3. **No ordering.** Retries, parallel workers, and replays all reorder events.
4. **Recipients are fixed at publish.** Subscription changes affect later events only.
5. **Endpoint state is read fresh.** URL, secrets, and pause or delete take effect at the next attempt.

Receivers handle rules 2 and 3 by [processing each `event.id` once](/docs/guides/receive#process-each-event-once).

## Retries

A delivery is `pending` until a worker sends it (`in_flight`), then ends `succeeded`, `failed`, or `cancelled` (the endpoint was deleted). Each attempt's response decides what happens next:

| Response                                  | Result                                      |
| ----------------------------------------- | ------------------------------------------- |
| `2xx`                                     | `succeeded`                                 |
| Network error, `408`, `425`, `429`, `5xx` | Back to `pending` until the next retry time |
| Any other `4xx`                           | `failed`, no retry                          |
| `3xx`                                     | `failed`. Redirects are never followed      |

By default a delivery gets up to seven attempts within 24 hours:

| Attempt | 1   | 2   | 3   | 4    | 5   | 6    | 7    |
| ------- | --- | --- | --- | ---- | --- | ---- | ---- |
| Waits   | now | 1 s | 5 s | 30 s | 2 m | 10 m | 30 m |

Change it with `retry: { delaysMs, maxAgeMs }` on `createWebhooks()` or `createDelivery()`. Every retry keeps the event ID and body and gets a fresh timestamp and signature.

## Publication

`matchRecipients()` runs once, when you publish. It returns every subscribed endpoint in the scope, paused ones included, and the list is stored with the event.

- If endpoint management can't be reached, `publish()` throws. An outage never turns into "no recipients".
- Endpoint edits made at the same moment may or may not be seen. There is no scope-wide snapshot.
- A repeated [`idempotencyKey`](/docs/guides/publish#make-retries-of-your-code-safe) returns the original event without looking up recipients again, even if management storage is down.
- [Inside your transaction](/docs/guides/publish#publish-inside-your-transaction), only delivery storage joins the commit. A Better Auth or second-database write does not.

## Endpoint changes while work is queued

| Change                | Effect on queued deliveries                                                |
| --------------------- | -------------------------------------------------------------------------- |
| Pause                 | Held until resume, or until the delivery passes its age limit              |
| Resume                | Eligible deliveries send again                                             |
| Delete                | Pending work is cancelled when the worker sees it. Secrets are cleared     |
| Change URL            | The next attempt uses the new URL                                          |
| Change subscriptions  | Later events only. Already accepted recipients stay                        |
| Rotate signing secret | The next attempt signs with the current secrets (both, during the overlap) |

A request already being sent when you pause or delete can still arrive. If endpoint management is unreachable at attempt time, the delivery waits without using up an attempt. An outage is never treated as a deletion.
