---
title: Delivery guarantees
description: What an accepted publication promises, what it does not, and how endpoint changes interact with queued work.
---

Short version: **at least once, no ordering**. An accepted publication durably records the event and its recipient set. The worker will keep trying each delivery within its retry budget. A receiver may see the same event more than once and must deduplicate by `webhook-id`.

## Publication

When `publish()` returns without a transaction option, the event and one pending delivery per recipient are committed in PostgreSQL. When you pass your own transaction, they are written but not committed until you commit.

Recipient selection happens once, at publication:

- The source returns **every** matching endpoint in the scope, including paused ones. A provider must not truncate the result or turn a lookup failure into an empty set.
- Concurrent endpoint edits may land before or after the lookup. The contract does not promise a scope-wide snapshot.
- The recipient IDs are committed with the event. Later subscription changes do not alter them.

### Idempotency

Repeating `publish()` with the same scope, `idempotencyKey`, event type, and validated payload returns the original event with `duplicate: true`. Recipients are not selected again, so the repeat succeeds even if management storage is down. The same key with different content throws `IDEMPOTENCY_CONFLICT`.

Keys stay reserved while the event is retained. [Pruning](/docs/operations/retention) releases them. If your business needs longer deduplication, keep your own record.

## Delivery

The worker retries network failures and `408`, `425`, `429`, and `5xx` responses on the configured schedule, up to the attempt and age limits. Other `4xx` responses fail the delivery without a retry. Redirects are never followed.

A receiver can process a request and then lose the response. The next attempt repeats the same event ID and body with a fresh timestamp and signature. This is why [receivers must deduplicate](/docs/guides/receive#commit-before-you-acknowledge).

Deliveries to different endpoints, retries, parallel workers, and replays can all reorder arrival. Do not rely on order.

## Endpoint changes while work is queued

Management records a change immediately. The worker resolves current endpoint state before every attempt, so the change takes effect at the next attempt:

| Change                | Effect on queued deliveries                                                          |
| --------------------- | ------------------------------------------------------------------------------------ |
| Pause                 | Held until the endpoint resumes or the delivery exceeds its age limit                |
| Resume                | Eligible deliveries send again                                                       |
| Delete                | Pending work is cancelled when the worker observes the deletion. Secrets are cleared |
| Change URL            | The next attempt uses the new URL                                                    |
| Change subscriptions  | Future publications use the new list. Already accepted recipients stay fixed         |
| Rotate signing secret | The next attempt signs with the current secrets (both during the overlap)            |

A request already prepared when you pause or delete can still arrive. A management call cannot recall it.

Provider failures are not endpoint changes. If the source cannot be reached, the delivery is deferred without consuming a receiver attempt, and the failure is reported to the worker host. An outage is never treated as a deletion or an empty recipient set.

## Transactions

`publish(input, { transaction })` runs inside a PostgreSQL transaction you own. Good Webhooks uses a savepoint so a failed publication does not poison your transaction. A successful return means the rows are written in that transaction, not committed.

The transaction covers delivery storage only. Management lookup is a separate provider call, and a Better Auth or second-database write is not made atomic with it. See [publish events](/docs/guides/publish#publish-inside-your-transaction).
