title: Architecture
description: Endpoint management and delivery have separate responsibilities and storage.
---

Good Webhooks separates the registration of destinations from the work of sending events. This lets an application use Better Auth for management while choosing its own sender, or use the built-in PostgreSQL delivery engine.

## Endpoint management

Management owns an endpoint's URL, scope, subscriptions, lifecycle state, and encrypted signing secrets. It creates no events, deliveries, or attempts.

The [Better Auth plugin](/better-auth/first-endpoint) stores endpoints through the host's adapter and adds authenticated HTTP routes. The [standalone PostgreSQL provider](/management/endpoints) stores endpoints in `webhook_endpoints`. Both use the same lifecycle API.

An `EndpointSource` exposes the two operations a sender needs. `matchRecipients` selects matching endpoint IDs during publication. `resolveEndpoint` obtains current state, URL, and signing secrets before an attempt. The source is a trusted server capability because it returns plaintext signing material.

## Delivery

The [delivery engine](/reference/delivery) validates event payloads, records accepted events and their deliveries in PostgreSQL, and sends signed HTTP requests. Workers own retries, attempt history, and queue cleanup. The host starts workers explicitly.

The producer reports an **event**. The sender creates one **delivery** for each selected endpoint. A delivery can require several **attempts**. A retry is another attempt within the same delivery. A replay creates another delivery for the original event.

Delivery storage is separate from management storage. They can use one PostgreSQL database and schema, different schemas, or different databases. Better Auth management can also use a supported non-PostgreSQL adapter while delivery uses PostgreSQL.

## Composition

`createWebhooks` combines both interfaces. Without a `management` option, it creates standalone PostgreSQL management with the same database and schema as delivery. With an injected provider, it uses that provider's source and exposes its endpoint operations.

`createDelivery` accepts only the sender dependencies, including an `EndpointSource`. This is enough for an independent worker process.

| The library owns                                                 | Your application owns                                                   |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Endpoint lifecycle and the sender contract                       | Authorization before trusted server calls                               |
| Event validation, queue records, signatures, and retry decisions | Business transaction boundaries and publication timing                  |
| Worker execution when called                                     | Worker startup, error reporting, shutdown, and database pool lifetime   |
| Migration SQL generation and compatibility checks                | Migration execution and upgrade planning                                |
| Signature verification and payload parsing                       | Request limits, durable receiver deduplication, and business processing |

Constructors do not start listeners, apply migrations, or start workers. See [delivery guarantees](/concepts/delivery-guarantees) for the boundaries of accepted publication and HTTP delivery.
