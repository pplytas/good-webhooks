---
title: Transactional recipient selection
description: Choose recipients from your own routing table inside the same PostgreSQL transaction that commits the business write.
---

Normally an event goes to every endpoint subscribed to its type. Use this recipe when **who receives it depends on the payload** or on rows you haven't committed yet, for example sending `invoice.paid` only to endpoints that handle the invoice's currency.

Inside one transaction you update the invoice, query your own routing table, and publish through a one-off `EndpointSource` that returns that list. The invoice, the event, and its deliveries then commit together. Your tables and the delivery tables must share one PostgreSQL database.

## Routing rules in your schema

An `invoice_routes` table owned by your application routes `invoice.paid` to endpoints whose currency and minimum amount match the invoice. Include every eligible endpoint, paused ones too, and check endpoint ownership when you create routes.

## Capture recipients, then publish

The function updates the invoice and queries routes on the transaction client, then publishes through a delivery instance whose `matchRecipients` returns that list. Each call gets its own source, so concurrent requests cannot overwrite each other.

<include cwd lang="ts" meta='title="examples/transactions/invoices.ts"'>
  ../../packages/good-webhooks/examples/transactions/invoices.ts
</include>

- `matchRecipients()` receives only the scope and event type. The closure supplies the selection and rejects any other scope or type.
- `resolveEndpoint()` delegates to the normal source, so it keeps returning current URLs, secrets, and status. Never capture the transaction client in it.

## Commit from the caller

```ts title="pay-invoice.ts"
import { recordInvoicePayment } from './invoices.js'

const pgClient = await pool.connect()
try {
  await pgClient.query('BEGIN')
  const publication = await recordInvoicePayment({
    database: pool,
    pgClient,
    source,
    organizationId: 'org_123',
    invoiceId: 'inv_123',
  })
  await pgClient.query('COMMIT')
  // Only now is the publication durable.
} catch (error) {
  await pgClient.query('ROLLBACK').catch(() => {})
  throw error
} finally {
  pgClient.release()
}
```

A rollback removes the invoice update, the event, and its deliveries together. If the transaction aborts, retry the whole operation with a fresh transaction; never reuse a captured selection. The routing query runs at your transaction's isolation level; default `READ COMMITTED` is enough unless the business rule needs more.

## Run the worker

The worker needs only the normal source and the same events, database, and schema:

```ts title="worker.ts"
import { createDelivery } from 'good-webhooks/delivery'
import { deliverySchema, events } from './invoices.js'

const delivery = createDelivery({ database: pool, schema: deliverySchema, events, source })
await delivery.worker.run({ signal: shutdown.signal })
```

It uses the committed recipient IDs and never reruns your routing query.
