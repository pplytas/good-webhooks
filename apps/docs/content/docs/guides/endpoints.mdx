An endpoint is a URL in one [scope](/docs/concepts/scopes) that subscribes to some of your event types. Endpoint management stores it with its status and encrypted signing secret. To let signed-in users manage their own endpoints, use the [Better Auth plugin](/docs/better-auth) instead.

## Register an endpoint

<Tabs groupId="management" persist items={['Combined client', 'Standalone provider']}>
<Tab>

The `webhooks` client from [installation](/docs/installation#create-the-client) has an `endpoints` API. The root client works in application scope; `forScope()` selects a named scope.

```ts
import { webhooks } from './webhooks.js'

const organization = webhooks.forScope({ type: 'organization', id: organizationId })

const { endpoint, secret } = await organization.endpoints.create({
  url: 'https://receiver.example/webhooks',
  description: 'Invoice notifications',
  eventTypes: ['invoice.paid'],
})
```

</Tab>
<Tab>

`createPostgresManagement()` stores endpoints without the delivery tables. Use it with a [custom sender](/docs/guides/custom-senders), or when endpoint management and delivery live in different databases.

```ts
import { createPostgresManagement } from 'good-webhooks/management/postgres'
import { pool } from './db.js'

const management = createPostgresManagement({
  database: pool,
  eventTypes: ['invoice.created', 'invoice.paid'],
  encryptionKey: process.env.WEBHOOK_ENCRYPTION_KEY!,
})
await management.check()

const { endpoint, secret } = await management.create(
  { type: 'organization', id: organizationId },
  { url: 'https://receiver.example/webhooks', eventTypes: ['invoice.paid'] },
)
```

It needs only the management table:

```sh
node -e 'import("good-webhooks/migrations").then(m => process.stdout.write(m.getPostgresMigration({ component: "management" })))' > 001-webhook-management.sql
psql "$DATABASE_URL" --single-transaction -v ON_ERROR_STOP=1 -f 001-webhook-management.sql
```

</Tab>
</Tabs>

Both need the storage encryption key from [installation](/docs/installation#create-a-storage-key), and every process that reads these endpoints needs the **same** key.

`create()` returns the plaintext signing secret once; no read returns it again. Show it to the endpoint owner once, or send it over a secure channel. Their receiver passes it to [`parseWebhook()`](/docs/guides/receive).

## Change an endpoint

```ts
await organization.endpoints.update(id, { eventTypes: ['invoice.created', 'invoice.paid'] })
await organization.endpoints.pause(id)
await organization.endpoints.resume(id)
const { secret } = await organization.endpoints.rotateSecret(id, { graceMs: 3_600_000 })
await organization.endpoints.remove(id)
```

| Method         | Effect                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------ |
| `update`       | Changes the URL, description, or subscriptions. A new URL is checked again                 |
| `pause`        | Keeps subscriptions and queued deliveries. The worker holds them until resume or expiry    |
| `resume`       | Checks the URL again, then queued deliveries send                                          |
| `rotateSecret` | Returns a new signing secret. Both sign requests during the overlap (default and max 24 h) |
| `remove`       | Permanent. Clears stored secrets, cancels queued deliveries, and keeps a deleted record    |

These calls return as soon as the record changes. A request already being sent can still arrive after a pause or remove. See [endpoint changes while work is queued](/docs/concepts/delivery-guarantees#endpoint-changes-while-work-is-queued).

## Automatic pauses

The worker pauses an endpoint when every attempt to it has failed for five days, or when it answers `410 Gone`. Nothing is deleted. Subscriptions and queued deliveries stay, and `resume` works as usual once the receiver works again. `pauseReason` tells the two kinds of pause apart:

| `pauseReason` | Meaning                                       |
| ------------- | --------------------------------------------- |
| `'owner'`     | Paused with `pause()`                         |
| `'failing'`   | Every attempt failed for the whole period     |
| `'gone'`      | The receiver answered `410 Gone`              |
| `null`        | Not paused, or paused before schema version 5 |

To tell the owner when it happens, use the [`onEndpointPaused` hook](/docs/guides/hooks#tell-owners-about-automatic-pauses). Hooks are best-effort, so an endpoint list that shows `pauseReason` is the reliable record. Set `endpointHealth: { pauseAfterMs }` to change the period, or `endpointHealth: false` to turn automatic pauses off. The [delivery reference](/docs/reference/delivery#automatic-pauses) has every option.

## Limits

A scope holds at most 1,000 live endpoints, and each endpoint subscribes to 1 to 100 of your configured event names. URLs must use HTTPS, carry no credentials, and be at most 2,048 characters. The [management reference](/docs/reference/management#inputs-and-limits) lists every limit.

## When a scope owner leaves

Standalone management doesn't know about your users. Call `removeScope(scope)` from your own deletion workflow to remove every endpoint in that scope:

```ts
import { createPostgresManagement } from 'good-webhooks/management/postgres'

const management = createPostgresManagement({ database: pool, eventTypes, encryptionKey })
await management.removeScope({ type: 'organization', id: organizationId })
```

The combined client doesn't expose `removeScope`. Build the provider with the same database, schema, and key as above, or create it first and pass it to `createWebhooks({ management })`.
