`good-webhooks/delivery` is the PostgreSQL sender: it publishes events, records deliveries, and runs workers against any endpoint source.

```ts
import { createDelivery } from 'good-webhooks/delivery'
import type {
  AttemptEvent,
  DeliveryEngine,
  DeliveryHooks,
  DeliveryOptions,
  DeliveryStats,
  EndpointHealthOptions,
  EndpointPausedEvent,
  EndpointSource,
  EndpointResolution,
  ManagementScope,
} from 'good-webhooks/delivery'
```

Shared event, database, query, and result types come from [`good-webhooks`](/docs/reference/core#other-root-exports). Every method on this page is also on the [`createWebhooks()`](/docs/reference/core) client.

## createDelivery

```ts
createDelivery<const E extends EventDefinitions>(options: DeliveryOptions<E>): DeliveryEngine<E>
```

```ts title="delivery.ts"
import { createDelivery } from 'good-webhooks/delivery'
import { createPostgresManagement } from 'good-webhooks/management/postgres'
import { Pool } from 'pg'
import { z } from 'zod'

const database = new Pool({ connectionString: process.env.DATABASE_URL })
const events = {
  'invoice.paid': z.object({ invoiceId: z.string(), amount: z.number().int() }),
}
const management = createPostgresManagement({
  database,
  eventTypes: Object.keys(events),
  encryptionKey: process.env.WEBHOOK_ENCRYPTION_KEY!,
})

export const delivery = createDelivery({ database, events, source: management.source })
```

Any [`EndpointSource`](/docs/reference/management#endpointsource) works as `source`, including [Better Auth management](/docs/better-auth/delivery). The constructor starts no work.

| Option                    | Default                                                          | Contract                                                                                                                                                                     |
| ------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `database`                | Required                                                         | PostgreSQL executor with `query()` and `connect()`. A checked-out client has `query()` and `release()`. `pg.Pool` satisfies this shape.                                      |
| `events`                  | Required                                                         | Nonempty map of event names to Standard Schema validators.                                                                                                                   |
| `source`                  | Required                                                         | Trusted `EndpointSource` with `matchRecipients` and `resolveEndpoint`.                                                                                                       |
| `schema`                  | `'public'`                                                       | PostgreSQL schema containing delivery tables.                                                                                                                                |
| `retry.delaysMs`          | `[5000, 300000, 1800000, 7200000, 18000000, 36000000, 36000000]` | At most 20 integer delays, each from 1 through 86,400,000 ms. An empty array disables retries.                                                                               |
| `retry.maxAgeMs`          | `172800000`                                                      | Retry window from 100 through 2,592,000,000 ms, counted from creation or from the first attempt after a pause. The default (48 hours) fits the default schedule with jitter. |
| `retry.respectRetryAfter` | `true`                                                           | Wait at least as long as a `429` or `503` response's `Retry-After` asks. See [attempt outcomes](#attempt-outcomes).                                                          |
| `endpointHealth`          | On                                                               | Automatic pauses, or `false` to turn them off. See [automatic pauses](#automatic-pauses).                                                                                    |
| `hooks`                   | None                                                             | Callbacks after each recorded outcome. See [hooks](#hooks).                                                                                                                  |
| `retentionMs`             | `604800000`                                                      | Event retention from 1,000 through 31,536,000,000 ms. Must be at least `retry.maxAgeMs`.                                                                                     |
| `allowLocalhost`          | `false`                                                          | Permits HTTP loopback destinations for development. Other private addresses stay forbidden.                                                                                  |
| `delivery`                | See below                                                        | Per-attempt and per-batch limits.                                                                                                                                            |

Event names match `^[a-zA-Z0-9][a-zA-Z0-9_.:-]{0,119}$`. The constructor validates each event's Standard Schema interface. Any invalid option throws `INVALID_CONFIG`. [Delivery guarantees](/docs/concepts/delivery-guarantees) explains how `retry` plays out.

## publish

```ts
publish(input: PublishInput<E>, options?: PublishOptions): Promise<PublishResult>
```

```ts
import { delivery } from './delivery.js'

const { eventId, deliveryCount, duplicate } = await delivery.publish({
  type: 'invoice.paid',
  data: { invoiceId: 'inv_123', amount: 4200 },
  idempotencyKey: 'invoice.paid:inv_123',
})
```

| Input or result        | Contract                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `input.type`           | A configured event name.                                                                                         |
| `input.data`           | The event validator's input type. The validator runs before anything is stored.                                  |
| `idempotencyKey`       | Nonblank string of at most 200 characters without null bytes. Unique within a scope while the event is retained. |
| `options.transaction`  | Optional PostgreSQL client inside an active `BEGIN` transaction. It must access the configured delivery tables.  |
| `result.eventId`       | Accepted event UUID.                                                                                             |
| `result.deliveryCount` | Number of original deliveries created for the accepted recipient set, including paused recipients. Can be zero.  |
| `result.duplicate`     | `true` when the same key already identifies the same event type and validated payload.                           |

The stored body is `{ id, type, occurredAt, data }`. `id` is the event UUID and `occurredAt` is an ISO timestamp assigned during publication.

The event and its original deliveries commit atomically within delivery storage. A caller-owned transaction stays uncommitted when `publish` returns. The [transaction and recipient guarantees](/docs/concepts/delivery-guarantees) also apply to duplicate publication. The [publish guide](/docs/guides/publish) shows idempotency keys and transactions in context.

| Error                  | When                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| `INVALID_INPUT`        | Unknown event type, payload rejected by the validator, payload outside the JSON limits, or an invalid key. |
| `IDEMPOTENCY_CONFLICT` | The key already identifies a different event type or payload in this scope.                                |
| `TRANSACTION_REQUIRED` | `options.transaction` has no active transaction.                                                           |
| Other errors           | Validator-thrown errors, source failures, and database failures propagate unchanged.                       |

<Accordions>
<Accordion title="Payload normalization and limits">

Payload normalization sorts object keys. It rejects nonfinite numbers, cycles, non-JSON values, nonplain objects, nesting beyond 64 levels, and JSON larger than 256 KiB. A publication validator can transform input, but its output must meet those JSON limits.

</Accordion>
<Accordion title="Publishing inside a caller-owned transaction">

`publish` runs in a savepoint on the supplied client, so a failed publication rolls back only its own writes. Recipient matching is a separate read through `source`, outside your transaction.

</Accordion>
</Accordions>

## deliveries

```ts
deliveries.list(query?: DeliveryQuery): Promise<Page<Delivery>>
deliveries.get(id: string): Promise<DeliveryDetail>
deliveries.replay(id: string): Promise<Delivery>
deliveries.replayMany(input: ReplayManyInput): Promise<ReplayManyResult>
deliveries.stats(): Promise<DeliveryStats>
```

```ts
import { delivery } from './delivery.js'

const page = await delivery.deliveries.list({ status: 'failed', limit: 25 })
const detail = await delivery.deliveries.get(page.items[0]!.id)
if (detail.replayOf === null) await delivery.deliveries.replay(detail.id)
```

### list

| `DeliveryQuery` field | Contract                                                      |
| --------------------- | ------------------------------------------------------------- |
| `endpointId`          | Only deliveries to this endpoint.                             |
| `eventId`             | Only deliveries of this event UUID.                           |
| `status`              | One delivery status.                                          |
| `limit`               | Integer from 1 through 100. Default 25.                       |
| `before`              | Exclusive delivery-ID cursor. Pass the previous `nextCursor`. |

`list` returns newest delivery IDs first. The result is `{ items, nextCursor }`; `nextCursor: null` marks the final page. Invalid query values throw `INVALID_INPUT`.

### get

`get` returns the delivery with its `attempts` array in attempt-number order. Delivery IDs are positive PostgreSQL bigint strings. A missing record in the selected scope produces `NOT_FOUND`.

### replay

`replay` sends the original event to the same endpoint again as a new delivery. It keeps the event ID and body and gets a new delivery ID and retry budget. See [retries and replay](/docs/operations/retries-and-replay).

| Error                | When                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `NOT_FOUND`          | No delivery with this ID in the selected scope.                                                                         |
| `INVALID_STATE`      | The endpoint is not active, the delivery is a replay or not `succeeded` or `failed`, or the event is outside retention. |
| `REPLAY_IN_PROGRESS` | The original delivery already has a pending or in-flight replay.                                                        |

### replayMany

`replayMany` replays one page of an endpoint's original deliveries in one transaction, newest delivery IDs first. Each eligible delivery follows `replay`'s rules, and an ineligible one is skipped instead of failing the call. See [bulk replay](/docs/operations/retries-and-replay#bulk-replay).

| `ReplayManyInput` field | Contract                                                                         |
| ----------------------- | -------------------------------------------------------------------------------- |
| `endpointId`            | Required. Only original deliveries to this endpoint. Replays are never examined. |
| `status`                | `'failed'` (default) or `'succeeded'`.                                           |
| `since`                 | `Date`. Only deliveries with `createdAt` at or after it.                         |
| `until`                 | `Date`. Only deliveries with `createdAt` before it. Not earlier than `since`.    |
| `limit`                 | Deliveries examined per call, from 1 through 1,000. Default 100.                 |
| `before`                | Exclusive delivery-ID cursor. Pass the previous `nextCursor`.                    |

| `ReplayManyResult` field | Meaning                                                                                                  |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| `replayed`               | New replay deliveries created.                                                                           |
| `skipped`                | Examined deliveries whose event is outside retention or that already have a pending or in-flight replay. |
| `nextCursor`             | The last examined delivery ID when more remain, or `null`.                                               |

| Error           | When                                                                            |
| --------------- | ------------------------------------------------------------------------------- |
| `INVALID_INPUT` | A missing or invalid field, an unknown `status`, or `since` later than `until`. |
| `NOT_FOUND`     | The endpoint is deleted or unknown in the selected scope.                       |
| `INVALID_STATE` | The endpoint is paused.                                                         |

### stats

`stats` summarizes the selected scope's retained deliveries for a status page or a backlog alert. The root client reports the application scope, and `forScope(scope).deliveries.stats()` reports that scope. There is no variant across scopes.

```ts
import { delivery } from './delivery.js'

const { deliveries, oldestPendingAgeMs, attemptsLastHour } = await delivery.deliveries.stats()
// deliveries: { pending: 12, in_flight: 2, succeeded: 4810, failed: 3, cancelled: 0 }
// oldestPendingAgeMs: 95000, or null when nothing is pending
// attemptsLastHour: { started: 2, succeeded: 140, retry: 6, failed: 1, abandoned: 0 }
```

| `DeliveryStats` field | Meaning                                                                                                                 |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `deliveries`          | Retained deliveries by status. Every status is present, `0` when none.                                                  |
| `oldestPendingAgeMs`  | Milliseconds since the oldest `pending` delivery was created, from the database clock. `null` when none is pending.     |
| `attemptsLastHour`    | Attempts started in the last hour by [outcome](#attempt-outcomes). `started` counts attempts still in flight. All keys. |

`pending` includes deliveries waiting for a retry and deliveries queued behind a paused endpoint. Replays count as deliveries. Deliveries and attempts come from two separate reads, so they can disagree slightly under load.

**Cost.** `stats` runs two queries without a transaction. The deliveries query reads every retained delivery of the scope. PostgreSQL reads the scope through its index when the scope is a small share of the table. When the scope holds most of the table, it scans the whole deliveries table instead. That is the usual case for an app that only uses application scope. The attempts query visits every retained attempt of the scope, because the last-hour filter has no index. As an order of magnitude, not a promise: with about 100,000 deliveries and 150,000 attempts in one scope, the deliveries query took tens of milliseconds and the attempts query under a quarter of a second on a local machine. Cost grows with retention, and [`prune()`](#prune) bounds it. Call it from a status page or a periodic check, not on every request.

### Delivery and attempt records

| Delivery field                | Type or meaning                                                          |
| ----------------------------- | ------------------------------------------------------------------------ |
| `id`, `endpointId`, `eventId` | String identifiers.                                                      |
| `eventType`                   | The event's type, such as `'invoice.paid'`.                              |
| `status`                      | `'pending'`, `'in_flight'`, `'succeeded'`, `'failed'`, or `'cancelled'`. |
| `attemptCount`                | Number of recorded attempts.                                             |
| `nextAttemptAt`, `createdAt`  | `Date` values.                                                           |
| `replayOf`                    | Original delivery ID, or `null`.                                         |
| `lastError`                   | Last error text, or `null`.                                              |
| `lastStatus`                  | Last HTTP status, or `null`.                                             |
| `attempts`                    | `Attempt[]`. Only on `DeliveryDetail`, the result of `get`.              |

| Attempt field    | Type or meaning                                                      |
| ---------------- | -------------------------------------------------------------------- |
| `number`         | Attempt number, starting at 1.                                       |
| `startedAt`      | `Date`.                                                              |
| `finishedAt`     | `Date`, or `null` while the attempt runs.                            |
| `outcome`        | `'started'`, `'succeeded'`, `'retry'`, `'failed'`, or `'abandoned'`. |
| `responseStatus` | HTTP status, or `null`.                                              |
| `responseBody`   | Captured response text bounded by `maxResponseBytes`, or `null`.     |
| `error`          | Error text, or `null`.                                               |

## deliverySettings

```ts
deliverySettings.get(endpointId: string): Promise<{ maxInFlight: number }>
deliverySettings.set(endpointId: string, settings: { maxInFlight: number }): Promise<{ maxInFlight: number }>
```

```ts
import { delivery } from './delivery.js'

const endpointId = 'ENDPOINT_ID' // From endpoints.create()
await delivery.deliverySettings.set(endpointId, { maxInFlight: 4 })
```

| Setting       | Default | Limits                     |
| ------------- | ------- | -------------------------- |
| `maxInFlight` | `2`     | Integer from 1 through 50. |

Stores sender-owned concurrency settings separately from endpoint records. Active and paused endpoints accept settings. Missing or deleted endpoints produce `NOT_FOUND`. An out-of-range value produces `INVALID_INPUT`.

These settings apply to all workers sharing the same delivery database and schema. They are distinct from the `delivery.concurrency` limit on each batch.

## worker

```ts
worker.runOnce(options?: {
	signal?: AbortSignal
	shutdownGraceMs?: number
}): Promise<WorkerResult>
worker.run(options: {
	signal: AbortSignal
	onError?: (error: unknown) => void
	pollIntervalMs?: number
	shutdownGraceMs?: number
}): Promise<void>
worker.prune(): Promise<number>
```

```ts title="worker.ts"
import { delivery } from './delivery.js'

const stop = new AbortController()
process.once('SIGTERM', () => stop.abort())

await delivery.worker.run({
  signal: stop.signal,
  onError: (error) => console.error('Webhook worker batch failed', error),
})
```

| Option            | Applies to                  | Default | Contract                                                                                   |
| ----------------- | --------------------------- | ------- | ------------------------------------------------------------------------------------------ |
| `signal`          | `run` (required), `runOnce` | None    | Abort to stop. An already-aborted signal returns without database work.                    |
| `onError`         | `run`                       | None    | Called with an internal batch failure. Without it, the failure stops `run`.                |
| `pollIntervalMs`  | `run`                       | `1000`  | Integer from 10 through 60,000 ms. The wait after an empty batch.                          |
| `shutdownGraceMs` | `run`, `runOnce`            | `30000` | Integer from 0 through 2,147,483,647 ms. Time for prepared attempts to finish after abort. |

All worker methods cover every scope in the configured delivery database and schema. Workers own neither the host's process signal handlers nor its database pool. The [workers guide](/docs/operations/workers) shows a supervised process.

### runOnce

`runOnce` recovers expired leases and processes one bounded batch. It does not drain the queue. Its `WorkerResult` contains these counts:

| Count       | Meaning                                                    |
| ----------- | ---------------------------------------------------------- |
| `claimed`   | Deliveries claimed in this batch.                          |
| `succeeded` | Attempts that got a `2xx`.                                 |
| `retried`   | Attempts that failed and were scheduled for a retry.       |
| `failed`    | Attempts that failed permanently or used up their retries. |
| `stale`     | Attempts whose claim no longer owns completion.            |

### run

`run` processes batches until its signal aborts. After a batch that completed at least one attempt, the next batch starts immediately; empty and stale-only batches wait `pollIntervalMs`. Without `onError`, an internal batch failure stops `run`. With it, the loop awaits the callback, waits `pollIntervalMs`, and continues; a callback that throws stops the loop.

### Attempt outcomes

| Response                                       | Attempt outcome                                                                |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| `2xx`                                          | `succeeded`                                                                    |
| `410`                                          | `failed`, no retry                                                             |
| Any other status, including `3xx` and `4xx`    | `retry` while retries remain, otherwise `failed`. Redirects are never followed |
| Network, DNS, or timeout error                 | `retry` while retries remain, otherwise `failed`                               |
| URL resolves to an unsafe address at send time | `failed`, no retry                                                             |
| Worker stopped or lease expired mid-request    | `abandoned`. The delivery retries if budget remains                            |

Each retry waits its configured delay plus up to 20% random jitter. When a `429` or `503` response carries a `Retry-After` header (seconds or an HTTP date) that asks for longer, the retry waits at least that long, plus the same jitter, unless `retry.respectRetryAfter` is `false`. The worker doesn't schedule a retry that would land after the retry window ends, so the delivery fails. The window is `retry.maxAgeMs`, counted from the delivery's creation, or from its first attempt after the endpoint was paused.

### Automatic pauses

The worker pauses an endpoint when every attempt to it has failed for `endpointHealth.pauseAfterMs`, or as soon as it answers `410 Gone`. The endpoint's [`pauseReason`](/docs/reference/management#results) becomes `'failing'` or `'gone'`, its queued deliveries wait, and its owner [resumes](/docs/guides/endpoints#automatic-pauses) it like any paused endpoint.

| `endpointHealth` field | Default     | Contract                                                         |
| ---------------------- | ----------- | ---------------------------------------------------------------- |
| `pauseAfterMs`         | `432000000` | Five days. Integer from 60,000 through 2,592,000,000 ms.         |
| `pauseOnGone`          | `true`      | Pause on the first `410` response instead of waiting the period. |

- Every attempt without a `2xx` counts as a failure, including timeouts, DNS errors, and unsafe addresses. `abandoned` attempts don't count.
- A success, a resume, or any change to the endpoint starts a new period. The pause applies only if the endpoint hasn't changed since the worker counted the failures. Both rely on the source's `revision`. With a source that reports none, only a success starts a new period.
- Pausing needs an endpoint source with [`pause()`](/docs/reference/management#endpointsource). The built-in PostgreSQL and Better Auth providers have it. `run()` and `runOnce()` throw `INVALID_CONFIG` for a source without it unless `endpointHealth` is `false`. An engine that only publishes never needs it.

### Hooks

```ts title="delivery.ts"
export const delivery = createDelivery({
  database,
  events,
  source: management.source,
  // metrics and notifyOwner stand for your own code.
  hooks: {
    onAttempt: ({ outcome, responseStatus, durationMs }) =>
      metrics.record('webhook.attempt', durationMs, { outcome, status: responseStatus }),
    onEndpointPaused: ({ scope, endpointId, reason }) => notifyOwner(scope, endpointId, reason),
  },
})
```

| Hook               | Called with                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onAttempt`        | `AttemptEvent`: `scope`, `endpointId`, `deliveryId`, `eventId`, `eventType`, `attempt`, `outcome`, `responseStatus`, `error`, and `durationMs`. Once per recorded attempt. |
| `onEndpointPaused` | `EndpointPausedEvent`: `scope`, `endpointId`, and `reason` (`'failing'` or `'gone'`). Once per automatic pause. Manual pauses don't call it.                               |

The worker awaits each hook after it commits the outcome. Hook errors join the batch errors, and a crash between the commit and the call skips the hook. The [hooks guide](/docs/guides/hooks) shows both hooks in use and explains [how they run](/docs/guides/hooks#how-hooks-run).

### prune

`prune` deletes at most 100 expired events and their dependent deliveries and attempts per call. It returns the number of removed events. Live leases or contended locks can defer deletion. It does not run automatically. See [clean up history](/docs/operations/retries-and-replay#clean-up-history).

### Worker errors

| Error            | When                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| `INVALID_INPUT`  | `pollIntervalMs` or `shutdownGraceMs` is out of range.                                                   |
| `INVALID_CONFIG` | Automatic pauses are on and the endpoint source has no `pause()`.                                        |
| `INVALID_STATE`  | This instance already has an active `run` loop or batch.                                                 |
| `AggregateError` | Internal failures in a batch, including hook and pause errors. Thrown after all sibling attempts settle. |

<Accordions>
<Accordion title="Shutdown and the grace period">

When the signal aborts, the worker stops taking new work and stops waiting for endpoint-provider results. Prepared attempts can finish during the grace period, which starts at the abort; then the worker cancels the remaining sends (`0` cancels at once). The grace period does not extend leases or bound database cleanup. Both methods await their completion writes before returning, and the host owns database timeouts, pool closure, and the process deadline. A cancelled send may have reached the receiver, so it can be attempted again.

</Accordion>
<Accordion title="Running several workers">

One worker instance cannot run overlapping `runOnce` calls or mix `runOnce` with an active `run` loop, including during shutdown. Separate instances coordinate through PostgreSQL leases and share each endpoint's `maxInFlight` limit.

</Accordion>
</Accordions>

## check and forScope

```ts
check(): Promise<void>
forScope(scope: Scope): Pick<DeliveryEngine<E>, 'publish' | 'deliveries' | 'deliverySettings'>
```

```ts
import { delivery } from './delivery.js'

await delivery.check()
const organization = delivery.forScope({ type: 'organization', id: 'org_123' })
await organization.deliveries.list()
```

`check()` verifies delivery schema version `6` and throws `SCHEMA_MISMATCH` otherwise, naming the SQL to apply. It never applies migrations and does not check management storage.

`forScope(scope)` returns `publish`, `deliveries`, and `deliverySettings` bound to one named scope. An invalid scope throws `INVALID_INPUT`. The root methods use application scope. Scope selection does not authorize access. See [scopes](/docs/concepts/scopes).
