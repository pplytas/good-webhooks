---
title: Better Auth plugin
description: Let signed-in users manage their own webhook endpoints through authenticated routes, stored in your existing Better Auth database.
---

The `goodWebhooks` plugin lets signed-in users manage their own webhook endpoints in your app. It adds one model and eight authenticated routes to your Better Auth instance and stores endpoints with your existing database adapter. To see it work first, run the [Better Auth quick start](/docs/better-auth/quick-start).

The plugin manages endpoints only; it sends nothing. To send events, add the [built-in delivery](/docs/better-auth/delivery) or a [custom sender](/docs/guides/custom-senders).

<Steps>
<Step>
### Install

```package-install
good-webhooks better-auth@1.7.10
```

Supports Better Auth `>=1.7.7 <1.8.0 || >=1.8.0-beta.0 <1.9.0-0`: 1.7.7 or later in 1.7, and 1.8 including the 1.8.0 betas.

</Step>
<Step>
### Add the server plugin

```ts title="auth.ts"
import { betterAuth } from 'better-auth'
import { goodWebhooks } from 'good-webhooks/better-auth'
import { eventTypes } from './event-types.js'

export const auth = betterAuth({
  database, // your existing database or adapter
  secret: process.env.BETTER_AUTH_SECRET!,
  plugins: [goodWebhooks({ eventTypes })], // [!code highlight]
})
```

```ts title="event-types.ts"
export const eventTypes = ['invoice.created', 'invoice.paid'] as const
```

Keep the tuple in its own module so the browser can import it without server code. `as const` carries the literal names into the client types. Routes appear under your auth handler's base path, for example `POST /api/auth/good-webhooks/create`.

</Step>
<Step>
### Generate and apply the schema

Use [Better Auth's CLI](https://better-auth.com/docs/concepts/cli) at your installed version:

```sh
npx auth@1.7.10 migrate --config ./src/auth.ts   # built-in SQL adapters
npx auth@1.7.10 generate --config ./src/auth.ts  # Drizzle or Prisma, then run their migrations
```

Keep every generated field and the unique `allocationKey` index; it enforces the per-scope endpoint limit under concurrent creates. Do not apply Good Webhooks' `management.sql` here: that file is for the standalone PostgreSQL provider.

</Step>
<Step>
### Add the client plugin

```ts title="auth-client.ts"
import { createAuthClient } from 'better-auth/client'
import { goodWebhooksClient } from 'good-webhooks/better-auth/client'
import { eventTypes } from './event-types.js'

export const authClient = createAuthClient({
  plugins: [goodWebhooksClient({ eventTypes })],
})
```

</Step>
<Step>
### Use it

<Tabs items={['Browser', 'Server']}>
<Tab>

```ts
const { data, error } = await authClient.goodWebhooks.create({
  url: 'https://receiver.example/webhooks',
  eventTypes: ['invoice.paid'],
})
data?.secret // show once, then never again
data?.endpoint.id

const endpoints = await authClient.goodWebhooks.list({})
```

</Tab>
<Tab>

Server-side calls go through `auth.api` with the request's session headers:

```ts
const created = await auth.api.createWebhookEndpoint({
  headers: request.headers,
  body: { url: 'https://receiver.example/webhooks', eventTypes: ['invoice.paid'] },
})
```

</Tab>
</Tabs>

An omitted `scope` means the signed-in user. Only create and rotate responses include the signing secret.

</Step>
</Steps>

## Options

| Option             | Default           | Purpose                                                                                               |
| ------------------ | ----------------- | ----------------------------------------------------------------------------------------------------- |
| `eventTypes`       | required          | Configured event names. Pass a literal tuple for typed clients                                        |
| `authorizeScope`   | deny              | Policy for application scope and custom scope types. See [permissions](/docs/better-auth/permissions) |
| `allowLocalhost`   | `false`           | Permit HTTP loopback URLs in development                                                              |
| `schema.modelName` | `webhookEndpoint` | Rename the model. Not a PostgreSQL namespace                                                          |
| `schema.fields`    |                   | Rename individual fields                                                                              |

Regenerate and apply the schema after changing `schema`. Your Better Auth database or ORM configuration decides where the model lives. The [plugin reference](/docs/reference/better-auth) has every route and error.

## Supported databases

The plugin stores endpoints through Better Auth's public adapter interface. On Node.js 24, with Better Auth 1.7.7 and the newest 1.7 and 1.8 releases, CI runs it against real SQLite, PostgreSQL 16, MySQL 8.4, MongoDB 8, SQL Server 2022, libSQL, and Cloudflare D1 (local Miniflare) databases, and through Drizzle and Prisma on PostgreSQL. Each run covers concurrent creates at the endpoint limit, revision-guarded updates, and maximum-length Unicode values.

<Callout type="warn" title="SQL Server needs a UTF-8 collation">
  Better Auth generates `varchar` columns, so a non-UTF-8 collation corrupts Unicode scope IDs,
  URLs, and descriptions. CI uses `Latin1_General_100_CI_AS_SC_UTF8`.
</Callout>

Bun's SQLite, hosted D1, remote Turso, MongoDB replica-set transactions, and Drizzle or Prisma on other databases are untested.
