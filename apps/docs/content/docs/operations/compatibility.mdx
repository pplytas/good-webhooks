Good Webhooks is preparing its first alpha release. Until it is published, use the [local archive](/getting-started/installation).

## Supported configurations

| Component             | Supported configuration | Verification                                                               |
| --------------------- | ----------------------- | -------------------------------------------------------------------------- |
| Node.js               | 24 or later             | Node.js 24 in CI, ESM and CommonJS consumers                               |
| TypeScript            | 5.9.3 or later          | 5.9.3 and the repository's 7.0.2 compiler, NodeNext and Bundler resolution |
| PostgreSQL components | PostgreSQL 16 and 17    | Full integration suite on both versions                                    |
| Better Auth           | `>=1.7.7 <1.8.0`        | Better Auth 1.7.7 and its [adapter matrix](/better-auth/database-adapters) |

TypeScript 5.9.3 is the oldest supported compiler. Earlier versions may work but are not checked. Standalone declaration checks run with `strict: true` and `skipLibCheck: false`. The Better Auth checks preserve application-level inference and rejection tests but use `skipLibCheck: true` for upstream declarations.

The repository's compiler version is a contributor requirement, not the minimum compiler for applications. The package ships JavaScript and declarations. Node.js 24 executes the shipped ESM and supports its CommonJS imports. Other JavaScript runtimes are not currently verified.

## Upgrade an alpha

Pin the exact alpha version in applications and commit the lockfile. Alpha releases can change the public API, behavior, and storage requirements. Read each release's notes before upgrading, and test the application's producers, workers, and receivers together. The latest alpha receives fixes; older alpha releases have no separate maintenance branches.

Published breaking changes must include migration guidance in the release notes. Package versions and database schema versions are separate. A package upgrade does not imply a database migration, and installing a package never applies SQL automatically.

## Upgrade storage

The initial alpha uses delivery schema version 3. The current SQL files initialize fresh installations. They do not upgrade older unpublished prototypes or their data.

For a future published schema change, use the version-specific upgrade instructions and migration SQL provided with that release. Apply the migration through your application's migration runner. Back up the database and follow the documented producer and worker rollout order. Do not assume that old and new workers can share a changed schema or that a downgrade is safe.

Call `check()` before starting PostgreSQL delivery. It rejects incompatible delivery storage and never changes the schema. Keep all processes on compatible package versions and the same configuration for their respective components. See [migrations](/operations/migrations).

## Delivery contract

Delivery is at least once, with no ordering guarantee. Keep receiver verification and deduplication in place across upgrades. Store signing and encryption secrets independently of deployments, and retain keys needed by existing endpoints. See [delivery guarantees](/concepts/delivery-guarantees) and [key rotation](/operations/key-rotation).
