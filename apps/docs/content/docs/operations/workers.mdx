---
title: Run workers
description: Start delivery explicitly, supervise it, shut it down without losing in-flight work, and know what each failure does.
---

Nothing is sent until a worker runs. A worker is a process you start: it claims due deliveries, resolves each endpoint, signs and sends the request, and records the attempt. You own the process, its database pool, and its supervision.

## The smallest worker

```ts title="worker.ts"
import { pool, webhooks } from './webhooks.js'

const stop = new AbortController()
process.once('SIGTERM', () => stop.abort())
process.once('SIGINT', () => stop.abort())

await webhooks.check() // fails fast if migrations are missing
await webhooks.worker.run({ signal: stop.signal }) // returns after a clean shutdown
await pool.end()
```

Run it as its own process next to your app. The [worker reference](/docs/reference/delivery#worker) lists every option. After a batch that made an attempt, `run()` starts the next batch at once; after an empty batch it waits `pollIntervalMs` (default 1 second). Run as many workers as you like: they coordinate through PostgreSQL leases, share the per-endpoint limits, and cover every scope in their database and schema.

`runOnce()` processes one bounded batch and returns counts, for schedulers and tests:

```ts
const result = await webhooks.worker.runOnce()
// { claimed, succeeded, retried, failed, stale }
```

Configure it through the environment:

| Variable                          | Required | Purpose                                                      |
| --------------------------------- | -------- | ------------------------------------------------------------ |
| `DATABASE_URL`                    | yes      | PostgreSQL connection string                                 |
| `WEBHOOK_ENCRYPTION_KEY`          | yes      | The key that encrypted the registered endpoints              |
| `WEBHOOK_SCHEMA`                  |          | Must match the migrations and the producer. Default `public` |
| `WEBHOOK_POLL_INTERVAL_MS`        |          | Wait after an empty batch. Default 1000                      |
| `WEBHOOK_DB_CONNECT_TIMEOUT_MS`   |          | Default 5000                                                 |
| `WEBHOOK_DB_STATEMENT_TIMEOUT_MS` |          | Default 10000. The client query timeout is one second longer |
| `WEBHOOK_ALLOW_LOCALHOST`         |          | `true` permits loopback HTTP receivers. Development only     |

Run it from a checkout with `node packages/good-webhooks/examples/operations/worker.ts`, or copy it and replace the event map with yours. It logs JSON lines (`webhooks.worker.started`, `webhooks.worker.failed`, `webhooks.worker.stopped`) without payloads or secrets; the library itself writes no logs. For Better Auth management, see [add delivery to Better Auth](/docs/better-auth/delivery#run-a-separate-worker).

<Callout type="warn">
  Never generate a fresh encryption key on startup. A wrong but well-formed key fails when the
  worker first decrypts an endpoint secret, not necessarily at startup.
</Callout>

## Shut down cleanly

Abort the signal to stop. The worker stops claiming, gives requests already being sent up to `shutdownGraceMs` (30 seconds by default), cancels the rest, records every outcome, and then `run()` resolves. Await it before closing the pool, and give your supervisor a kill deadline that covers the grace period, the final writes, and pool closure.

A cancelled request may still have reached the receiver. It is retried, which is one reason [receivers deduplicate](/docs/guides/receive#process-each-event-once).

## What failures do

Without `onError`, an internal failure rejects `run()` and the process exits; let your supervisor restart it with backoff. If you pass `onError` to log and continue, watch that deliveries keep moving. Receiver failures are not internal failures; they follow the [retry policy](/docs/concepts/delivery-guarantees#retries), and an endpoint that keeps failing is [paused automatically](/docs/guides/endpoints#automatic-pauses). The worker reports errors thrown by [hooks](/docs/reference/delivery#hooks) like internal failures, after it records the outcome.

For metrics and logs per attempt, pass an `onAttempt` [hook](/docs/reference/delivery#hooks) to the engine. It receives the outcome, status, error, and duration of every attempt.

Every failure below ends with the delivery retried under the same event ID, or the process exiting for a supervisor to restart. Each row is [checked by a test](https://github.com/pplytas/good-webhooks/blob/main/docs/operations.md#where-each-failure-claim-is-checked).

| Situation                                 | What happens                                                                                 |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| Worker killed mid-request                 | The attempt is `abandoned` when its lease expires, and another worker retries the delivery.  |
| Worker killed after the receiver accepted | Same. The receiver sees the same `event.id` twice, and its deduplication absorbs it.         |
| Receiver hangs                            | The request is cancelled at `timeoutMs` and retried on schedule.                             |
| Database connection drops                 | `run()` rejects. The half-finished attempt is recovered when its lease expires.              |
| Database unreachable or locked at startup | `check()` fails within your connection or statement timeout, before anything is claimed.     |
| Wrong encryption key                      | The worker exits without consuming an attempt.                                               |
| `SIGTERM` during a request                | The request gets `shutdownGraceMs` to finish, its outcome is recorded, and `run()` resolves. |
| `SIGKILL`                                 | Leases are left behind and recovered by the next worker after `leaseMs`.                     |
| Schema older or newer than the package    | `check()` throws `SCHEMA_MISMATCH` naming the SQL to apply.                                  |

A worker claims a delivery by writing an attempt with a lease before sending. If it dies, the lease expires after `leaseMs` (60 seconds by default) and the next batch recovers it. Lease tokens are fenced: a late worker whose lease expired cannot record a result, so two workers never both record success for one attempt.

These behaviors are verified on a single PostgreSQL instance with local receivers. They do not cover database failover or throughput limits. Workers never prune history; schedule [cleanup](/docs/operations/retries-and-replay#clean-up-history) separately.
