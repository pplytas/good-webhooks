---
title: Run workers
description: Start delivery explicitly, supervise it, and shut it down without losing in-flight work.
---

Nothing sends until a worker runs. You own the process, its database pool, and its supervision. Apply [migrations](/docs/operations/migrations) before starting one.

## One batch or a loop

```ts
// One bounded batch. Call it from a scheduler if work remains.
const result = await webhooks.worker.runOnce()
result.succeeded // also claimed, retried, failed, stale

// Continuous processing until the signal aborts.
const stop = new AbortController()
await webhooks.worker.run({
  signal: stop.signal,
  pollIntervalMs: 1000,
  shutdownGraceMs: 30_000,
})
```

`run()` starts the next batch immediately after a batch completes at least one attempt. After an empty batch, or an error handled by `onError`, it waits `pollIntervalMs`. Receiver retries keep their own schedule regardless of polling.

Workers process every scope in their delivery database and schema. Several workers coordinate through PostgreSQL leases and share per-endpoint concurrency limits. No database transaction is held open during an HTTP request.

Configure it through the environment:

| Variable                          | Required | Purpose                                                      |
| --------------------------------- | -------- | ------------------------------------------------------------ |
| `DATABASE_URL`                    | yes      | PostgreSQL connection string                                 |
| `WEBHOOK_ENCRYPTION_KEY`          | yes      | The key that encrypted the registered endpoints              |
| `WEBHOOK_SCHEMA`                  |          | Must match the migrations and the producer. Default `public` |
| `WEBHOOK_POLL_INTERVAL_MS`        |          | Wait after an empty batch. Default 1000                      |
| `WEBHOOK_DB_CONNECT_TIMEOUT_MS`   |          | Default 5000                                                 |
| `WEBHOOK_DB_STATEMENT_TIMEOUT_MS` |          | Default 10000. The client query timeout is one second longer |
| `WEBHOOK_ALLOW_LOCALHOST`         |          | `true` permits loopback HTTP receivers. Development only     |

Run it from a checkout with `node packages/good-webhooks/examples/operations/worker.ts`, or copy it and replace the event map with yours.

<Callout type="warn">
  Never generate a fresh encryption key on startup. A wrong but well-formed key fails when the
  worker first decrypts an endpoint secret, not necessarily at startup.
</Callout>

For Better Auth management, the worker also constructs the auth instance and provider. See [add delivery to Better Auth](/docs/better-auth/delivery#run-a-separate-worker).

## Handle failures

Without `onError`, an internal failure rejects `run()` and the process exits. Let your supervisor restart it with backoff. If you pass `onError` to log and continue, watch that deliveries keep making progress. Receiver failures are not internal failures; they follow the retry policy.

Errors are emitted as JSON lines (`webhooks.worker.started`, `webhooks.worker.failed`, `webhooks.worker.stopped`) without configuration, payloads, or secrets.

## Shut down cleanly

Abort the signal to stop. The worker then:

1. stops claiming new work and stops waiting on endpoint-provider lookups,
2. lets already-prepared attempts finish for up to `shutdownGraceMs` (default 30 seconds),
3. cancels remaining sends and records their outcome,
4. returns after owned work and completion writes finish.

Await the worker before closing the pool. Then give your supervisor a final deadline that covers the grace period, database writes, pool closure, and your own cleanup. The grace period is not a process exit deadline.

A cancelled HTTP request may still have been processed by the receiver. Such attempts are retried, which is one more reason [receivers deduplicate](/docs/guides/receive#commit-before-you-acknowledge).
