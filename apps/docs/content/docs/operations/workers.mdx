---
title: Run workers
description: Start delivery explicitly, supervise it, and shut it down without losing in-flight work.
---

Nothing is sent until a worker runs. A worker is a process you start: it claims due deliveries, sends them, records each attempt, and schedules retries. You own the process, its database pool, and its supervision.

## The smallest worker

```ts title="worker.ts"
import { pool, webhooks } from './webhooks.js'

const stop = new AbortController()
process.once('SIGTERM', () => stop.abort())
process.once('SIGINT', () => stop.abort())

await webhooks.check() // fails fast if migrations are missing
await webhooks.worker.run({ signal: stop.signal }) // returns after a clean shutdown
await pool.end()
```

Run it as its own process next to your app, and apply [migrations](/docs/operations/migrations) first. `run()` also takes `pollIntervalMs`, `shutdownGraceMs`, and `onError`; see the [worker reference](/docs/reference/delivery#worker).

<Flow title="What run() does in a loop">
  <FlowStep title="Claim">
    Lease due deliveries, respecting each endpoint's in-flight limit.
  </FlowStep>
  <FlowStep title="Resolve">Read each endpoint's current URL, status, and secrets.</FlowStep>
  <FlowStep title="Send">Sign and POST. No database transaction is held open meanwhile.</FlowStep>
  <FlowStep title="Record">Store the attempt; mark succeeded, failed, or due for retry.</FlowStep>
</Flow>

After a batch that made at least one attempt, `run()` starts the next batch at once. After an empty batch, it waits `pollIntervalMs` (default 1 second). Retries keep their own schedule regardless.

Workers handle every scope in their delivery database and schema. Run as many as you like: they coordinate through PostgreSQL leases and share the per-endpoint limits.

## One batch instead of a loop

`runOnce()` processes one bounded batch and returns counts. Use it from a scheduler or in tests:

```ts
const result = await webhooks.worker.runOnce()
// { claimed, succeeded, retried, failed, stale }
```

The package ships a complete entrypoint. It validates configuration, listens for signals, checks the schema, runs, and exits nonzero on failure after closing its pool.

Configure it through the environment:

| Variable                          | Required | Purpose                                                      |
| --------------------------------- | -------- | ------------------------------------------------------------ |
| `DATABASE_URL`                    | yes      | PostgreSQL connection string                                 |
| `WEBHOOK_ENCRYPTION_KEY`          | yes      | The key that encrypted the registered endpoints              |
| `WEBHOOK_SCHEMA`                  |          | Must match the migrations and the producer. Default `public` |
| `WEBHOOK_POLL_INTERVAL_MS`        |          | Wait after an empty batch. Default 1000                      |
| `WEBHOOK_DB_CONNECT_TIMEOUT_MS`   |          | Default 5000                                                 |
| `WEBHOOK_DB_STATEMENT_TIMEOUT_MS` |          | Default 10000. The client query timeout is one second longer |
| `WEBHOOK_ALLOW_LOCALHOST`         |          | `true` permits loopback HTTP receivers. Development only     |

Run it from a checkout with `node packages/good-webhooks/examples/operations/worker.ts`, or copy it and replace the event map with yours.

<Callout type="warn">
  Never generate a fresh encryption key on startup. A wrong but well-formed key fails when the
  worker first decrypts an endpoint secret, not necessarily at startup.
</Callout>

For Better Auth management, the worker also constructs the auth instance and provider. See [add delivery to Better Auth](/docs/better-auth/delivery#run-a-separate-worker).

## Handle failures

Without `onError`, an internal failure rejects `run()` and the process exits. Let your supervisor restart it with backoff. If you pass `onError` to log and continue, watch that deliveries keep making progress. Receiver failures are not internal failures; they follow the retry policy.

The example entrypoint logs JSON lines (`webhooks.worker.started`, `webhooks.worker.failed`, `webhooks.worker.stopped`) without configuration, payloads, or secrets. The library itself writes no logs.

## Shut down cleanly

Abort the signal to stop:

<Flow>
  <FlowStep title="Stop claiming">
    No new deliveries; pending endpoint lookups are abandoned.
  </FlowStep>
  <FlowStep title="Grace period">
    Requests already being sent get up to `shutdownGraceMs` (30 s default).
  </FlowStep>
  <FlowStep title="Cancel">Remaining requests are cancelled and their outcome recorded.</FlowStep>
  <FlowStep title="Return">`run()` resolves after its database writes finish.</FlowStep>
</Flow>

Await the worker before closing the pool. Then give your supervisor a final deadline that covers the grace period, database writes, pool closure, and your own cleanup. The grace period is not a process exit deadline.

A cancelled HTTP request may still have been processed by the receiver. Such attempts are retried, which is one more reason [receivers deduplicate](/docs/guides/receive#process-each-event-once).
