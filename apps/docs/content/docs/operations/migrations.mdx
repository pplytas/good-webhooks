---
title: Migrations
description: Pick the SQL for the components you run, apply it with your own migration runner, and keep runtime schema names in sync.
---

Good Webhooks never applies DDL. `getPostgresMigration()` returns SQL text; the shipped `.sql` files are the same output for the default `public` schema. Your migration runner applies it once.

## Which SQL do I need?

| Setup                                              | Management                               | Delivery                               |
| -------------------------------------------------- | ---------------------------------------- | -------------------------------------- |
| Standalone management and delivery, same schema    | `001-initial.sql` (both components)      |                                        |
| Standalone management only                         | `management.sql`                         | none                                   |
| Better Auth management only                        | Better Auth or ORM schema workflow       | none                                   |
| Better Auth management with Good Webhooks delivery | Better Auth or ORM schema workflow       | `delivery.sql`                         |
| Management and delivery in separate schemas        | generated with `component: 'management'` | generated with `component: 'delivery'` |

Never apply the combined file and a component file to the same installation.

## Generate SQL

```ts
import { getPostgresMigration } from 'good-webhooks/migrations'

const sql = getPostgresMigration() // both components, schema 'public'
const deliveryOnly = getPostgresMigration({ component: 'delivery', schema: 'notifications' })
```

Or from the shell:

```sh
node -e 'import("good-webhooks/migrations").then(m => process.stdout.write(m.getPostgresMigration()))' > 001-webhooks.sql
psql "$DATABASE_URL" --single-transaction -v ON_ERROR_STOP=1 -f 001-webhooks.sql
```

The SQL has no `BEGIN` or `COMMIT`. Wrap it in one transaction with your migration ledger entry. Every script starts with `CREATE SCHEMA IF NOT EXISTS`; table creation itself is not idempotent.

The shipped files are also package exports, resolvable with `import.meta.resolve('good-webhooks/migrations/delivery.sql')` for migration tools that read files.

## Match the runtime schema

Whatever schema you generate for must be the schema you configure at runtime:

```ts
const schema = 'notifications'
const sql = getPostgresMigration({ schema })

const webhooks = createWebhooks({ database: pool, schema, encryptionKey, events })
```

Management and delivery can use different schemas or different databases:

```ts
const management = createPostgresManagement({
  database: managementDatabase,
  schema: 'management',
  eventTypes: Object.keys(events),
  encryptionKey,
})
const delivery = createDelivery({
  database: deliveryDatabase,
  schema: 'delivery',
  source: management.source,
  events,
})
```

An injected management provider keeps its own schema. Delivery's `schema` option never moves it. For Better Auth, the model's placement comes from your Better Auth database or ORM configuration; generate only the delivery SQL.

## Check before you start

```ts
await webhooks.check()
```

`check()` verifies that the expected tables and columns exist and that the delivery schema version is `3`. It throws `SCHEMA_MISMATCH` otherwise and never changes anything. Call it at startup in the app and in every worker.

## Upgrades

The current SQL initializes fresh storage. It does not upgrade pre-release prototype schemas. A future schema change will ship its own upgrade SQL and a rollout order for producers and workers. Package versions and schema versions are independent: installing a new package never runs SQL. See [compatibility](/docs/operations/compatibility) and the [migration reference](/docs/reference/migrations).
