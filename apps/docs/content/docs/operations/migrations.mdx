title: Migrations
description: Pick the SQL for the components you run, apply it with your own migration runner, and keep runtime schema names in sync.
---

Good Webhooks never applies DDL. `getPostgresMigration()` returns SQL text, the shipped `.sql` files hold the same SQL for the `public` schema, and your migration runner applies it once.

## Which SQL do I need?

| Setup                                              | Management                               | Delivery                               |
| -------------------------------------------------- | ---------------------------------------- | -------------------------------------- |
| Standalone management and delivery, same schema    | `001-initial.sql` (both components)      |                                        |
| Standalone management only                         | `management.sql`                         | none                                   |
| Better Auth management only                        | Better Auth or ORM schema workflow       | none                                   |
| Better Auth management with Good Webhooks delivery | Better Auth or ORM schema workflow       | `delivery.sql`                         |
| Management and delivery in separate schemas        | generated with `component: 'management'` | generated with `component: 'delivery'` |

Never apply the combined file and a component file to the same installation.

## Generate SQL

```ts
import { getPostgresMigration } from 'good-webhooks/migrations'

const sql = getPostgresMigration() // both components, schema 'public'
const deliveryOnly = getPostgresMigration({ component: 'delivery', schema: 'notifications' })
```

Or from the shell:

```sh
node -e 'import("good-webhooks/migrations").then(m => process.stdout.write(m.getPostgresMigration()))' > 001-webhooks.sql
psql "$DATABASE_URL" --single-transaction -v ON_ERROR_STOP=1 -f 001-webhooks.sql
```

The SQL has no `BEGIN` or `COMMIT`, so wrap it in one transaction with your migration ledger entry. Table creation is not idempotent. Migration tools that read files can resolve the shipped files, for example `import.meta.resolve('good-webhooks/migrations/delivery.sql')`.

## Match the runtime schema

The schema you generate for must be the schema you configure at runtime:

```ts
import { createWebhooks } from 'good-webhooks'
import { getPostgresMigration } from 'good-webhooks/migrations'

const schema = 'notifications'
const sql = getPostgresMigration({ schema }) // apply with your migration tool

const webhooks = createWebhooks({ database: pool, schema, encryptionKey, events })
```

Management and delivery can use different schemas or different databases:

```ts
const management = createPostgresManagement({
  database: managementDatabase,
  schema: 'management',
  eventTypes: Object.keys(events),
  encryptionKey,
})
const delivery = createDelivery({
  database: deliveryDatabase,
  schema: 'delivery',
  source: management.source,
  events,
})
```

An injected management provider keeps its own schema; delivery's `schema` option never moves it. For Better Auth, generate only the delivery SQL.

Call `await webhooks.check()` at startup in the app and in every worker. It verifies the tables and that each component records schema version `4`, and throws `SCHEMA_MISMATCH` naming the SQL to apply. It never changes anything.

## Upgrades

Installing a new package never runs SQL. When a release needs a newer schema, its notes say so, and `check()` on the new package refuses to start until the upgrade is applied.

Generate the upgrade from the version your database records:

```ts
import { getPostgresUpgrade } from 'good-webhooks/migrations'

const sql = getPostgresUpgrade({ from: 3 }) // both components in 'public'
```

The shipped equivalent is `good-webhooks/migrations/upgrades/004-all.sql`. Separate namespaces take `component` with their own `schema`. The SQL checks the recorded version first, so applying it twice or against the wrong version rolls back.

### Rollout order

1. Deploy nothing yet. Apply the upgrade SQL with your migration runner in one transaction. Processes on the previous package keep running when the release notes say the upgrade is compatible with them; the 3 to 4 upgrade is.
2. Restart producers on the new package. Their `check()` now passes.
3. Restart workers and cleanup jobs on the new package. A restarted process on the old package fails fast with `SCHEMA_MISMATCH`, so finish the rollout rather than mixing versions for long.

A process that skips `check()` may run unsupported queries against a schema it doesn't know. CI rehearses this order against the previously published package. Every option is in the [migration reference](/docs/reference/migrations).
