---
title: Publish events
description: Define validated events, preserve idempotency, and commit publications with business writes.
---

Use a configured `createWebhooks` or `createDelivery` instance. Both expose the same publication methods. Follow [standalone setup](/getting-started/first-delivery) or [Better Auth delivery setup](/better-auth/add-delivery) first.

## Define payload schemas

Keep event definitions in a shared module:

```ts title="events.ts"
import { z } from 'zod'

export const events = {
  'invoice.paid': z.object({
    invoiceId: z.string(),
    amount: z.number().int().nonnegative(),
  }),
}
```

Pass this map to the delivery factory. Standard Schema validators provide both TypeScript inference and runtime validation. Validated output must be JSON, fit within 256 KiB, and have a maximum depth of 64.

Prefer schemas that preserve values when sharing the map with receivers. Normalize domain inputs before publication, or maintain a receiver schema that accepts the producer's transformed output.

## Publish with an idempotency key

```ts
const publication = await webhooks.publish({
  type: 'invoice.paid',
  data: { invoiceId: 'inv_123', amount: 4200 },
  idempotencyKey: 'invoice-paid:inv_123',
})
```

This root call selects application scope. For an owner-specific endpoint, use `webhooks.forScope({ type, id }).publish(...)` after authorizing the scope.

A repeat with the same scope, idempotency key, type, and validated payload returns the original event with `duplicate: true`. Different content with the same key throws `IDEMPOTENCY_CONFLICT`. Keys stay reserved while their events remain in storage.

`deliveryCount` is the number of selected recipients and may be zero. Acceptance means that delivery storage contains the event and its deliveries. It does not mean a receiver accepted an HTTP request. Start a [worker](/operations/workers) explicitly.

Recipient lookup includes paused subscriptions. Idempotent repeats keep the original selection. See [recipient selection guarantees](/concepts/delivery-guarantees) for concurrent management changes.

## Publish with a business transaction

Use this pattern when the business write and delivery tables use the same PostgreSQL database. Pass a checked-out client with an active transaction:

```ts
const client = await pool.connect()
try {
  await client.query('BEGIN')
  await client.query('UPDATE invoices SET paid = true WHERE id = $1', ['inv_123'])
  await webhooks.publish(
    {
      type: 'invoice.paid',
      data: { invoiceId: 'inv_123', amount: 4200 },
      idempotencyKey: 'invoice-paid:inv_123',
    },
    { transaction: client },
  )
  await client.query('COMMIT')
} catch (error) {
  await client.query('ROLLBACK')
  throw error
} finally {
  client.release()
}
```

The example assumes an application-owned `invoices` table. Use the configured delivery database and matching schema. Do not run concurrent operations on that client. You own commit and rollback.

Before commit, the returned publication is provisional and invisible to workers. Rolling back removes both the business write and queued delivery work.

Management lookup remains outside this transaction. This pattern does not create a transaction spanning Better Auth storage, a separate business database, and delivery storage. If those databases differ, use an application-owned durable outbox or another recovery workflow to bridge the commits.

## Limit endpoint concurrency

Delivery capacity belongs to the sender, not endpoint management:

```ts
await webhooks.deliverySettings.set(endpointId, { maxInFlight: 4 })
```

Select the endpoint's scope before changing its setting. The per-endpoint limit is shared across workers using the delivery database. Worker request concurrency remains a separate factory option. See [delivery settings and limits](/reference/delivery).
